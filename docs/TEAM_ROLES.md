# 온길 3인 팀 역할 분담

각자 한 영역의 최종 책임자(Owner)가 되되, 접근성은 전원의 공통 완료 조건으로 두는 구성을 권장합니다.

## 1. Next.js 프론트엔드·접근성 담당

**책임**

- Next.js App Router, React, TypeScript 화면 구조 및 컴포넌트 개발
- 경로 검색, 단계별 안내, 제보, 이미지 업로드 흐름 구현
- Web Speech API와 브라우저 상태 관리
- 키보드 탐색, 포커스, 스크린리더, 고대비·글자 확대 대응
- 반응형 화면과 이후 PWA 전환

**산출물**

- 접근 가능한 UI 컴포넌트
- 키보드·스크린리더 테스트 체크리스트
- Lighthouse와 수동 접근성 점검 결과

## 2. Node.js 백엔드·데이터 담당

**책임**

- Express API와 SQLite 스키마 관리
- 제보 등록·조회·상태·만료 정책
- 지도 경로 및 장소 검색 API 연동
- 이미지 업로드 검증과 Vision API 연동
- 입력 검증, 오류 응답, 위치정보 최소 수집

**산출물**

- API 명세와 ERD
- 외부 API 어댑터
- API 단위 테스트와 seed 데이터

## 3. 서비스 기획·통합·QA 담당

**책임**

- 사용자 인터뷰, 핵심 시나리오, MVP 우선순위 관리
- 짧고 구체적인 음성 안내 문구 기준 수립
- 프론트·백 통합 테스트와 배포 환경 관리
- 시각장애 당사자 관점 사용성 테스트
- 발표 자료, 데모 시나리오, 일정과 이슈 관리

**산출물**

- 사용자 여정과 MVP 범위 문서
- 통합 테스트 시나리오와 버그 보드
- 배포본, 데모 영상, 발표 자료

## 공통 완료 조건

- 마우스 없이 키보드만으로 사용할 수 있다.
- 버튼과 입력 목적이 스크린리더로 명확히 전달된다.
- 색상만으로 상태를 구분하지 않는다.
- 글자를 200% 확대해도 핵심 기능을 사용할 수 있다.
- 음성 안내에 방향, 기준점, 행동이 포함된다.
- 오류가 화면과 스크린리더 모두에 전달된다.
- 실제 안전 기능처럼 오인될 수 있는 데모에는 한계를 명시한다.

## 4주 일정 예시

| 주차 | 프론트엔드·접근성 | 백엔드·데이터 | 서비스·통합·QA |
|---|---|---|---|
| 1주차 | 디자인 시스템, 검색 화면 | DB·제보 API | 사용자 시나리오, 화면 설계 |
| 2주차 | 경로·음성 안내 | 지도 API 어댑터 | 안내 문구 기준, 1차 통합 |
| 3주차 | 제보·이미지 화면 | 이미지 분석 API | 접근성·사용성 테스트 |
| 4주차 | 반응형·오류 처리 | API 테스트·배포 | 통합 QA, 발표·데모 |

## 협업 규칙

- 기능 브랜치는 1~2일 안에 리뷰할 수 있는 크기로 유지합니다.
- Pull Request는 다른 담당자가 키보드와 오류 흐름까지 확인합니다.
- 실제 지도·AI API가 늦어져도 데모가 멈추지 않도록 mock을 유지합니다.
- 사용자 안전과 관련된 표현은 세 명이 함께 검토합니다.
